# Ядро, CPU и процессы

## Инициализация

Основная последовательность запуска находится в `kernel/core/main.c`:

1. Инициализация serial, драйверов, CPU и памяти.
2. PCI/NVMe и файловые системы.
3. Framebuffer и PS/2, если включены конфигурацией.
4. PIT, scheduler и стартовые user процессы.

Порядок важен: процессный загрузчик использует VFS, ELF loader, VMM и kernel heap, поэтому эти подсистемы должны быть готовы до запуска shell/desktop.

## x86_64 и per-CPU

`kernel/arch/x86_64/percpu.h` задаёт структуру `PerCpu`: self pointer, идентификаторы CPU, kernel stack top, user RSP save, текущие process/address-space pointers и счётчики. BSP сейчас является единственным инициализируемым CPU; `MAX_CPUS` оставляет место для SMP, но сам по себе SMP не включает.

Per-CPU база устанавливается через MSR GS base. `swapgs` используется при переходе между user и kernel GS состояниями. TSS `RSP0` задаёт kernel stack для входа из user mode.

## Прерывания и syscall

- IRQ stubs сохраняют регистры и передают управление `irq_dispatch`.
- PIT использует IRQ0 и увеличивает счётчик системных ticks.
- Исключения обрабатываются через exception stubs; page fault декодируется в `kernel/mm/pf.c`.
- Syscall ABI находится в `kernel/arch/x86_64/syscall.h` и пользовательских обёртках `user/sys.h`.
- `syscall_entry.S` сохраняет syscall context, вызывает C handler и возвращается через `sysretq`.

`SYS_YIELD` включает interrupts и ждёт событие (`sti; hlt; cli`), а не выполняет пустой цикл. PIT/IRQ даёт scheduler возможность переключить процесс. `SYS_WINDOW_RECV` для клиентов ожидает сообщение, а desktop server проверяет очередь неблокирующе, чтобы не остановить обработку ввода и рендер.

## Процессы и scheduler

Описания находятся в `kernel/tasking/process.h` и реализации в `process.c`/`scheduler.c`. Процесс содержит PID/PPID, состояние, address space, kernel stack, сохранённый IRQ frame, пользовательский контекст, FDs, cwd и список потомков.

Основные переходы:

- `process_create()` выделяет process object и kernel stack.
- `process_setup_initial_frame()` формирует стек, который восстанавливает `irq_return`.
- `scheduler_add()` ставит готовый процесс в очередь.
- `scheduler_tick()` пересчитывает virtual runtime и может переключить процесс.
- `sys_exit_impl()` помечает процесс завершённым и переключает выполнение на следующий.

Idle/blocked user processes не должны бесконечно крутить `SYS_WINDOW_RECV`/`SYS_YIELD`: это увеличивает число переключений и ухудшает отзывчивость при нескольких приложениях.

## Fork и exec

`fork` клонирует address space и формирует child context с `RAX=0`; parent получает PID ребёнка. `exec` открывает ELF через VFS, копирует аргументы из user memory, создаёт новый address space, отображает stack и ABI page, загружает ELF `PT_LOAD` segments и строит стек `argc/argv/envp`.

После успешной загрузки `exec` заменяет AS текущего процесса и обновляет syscall context для перехода к новому `RIP/RSP`. Нельзя вызывать `process_setup_initial_frame()` над активным syscall kernel stack: это может затереть текущие C/syscall frames.

ELF проверяется на x86_64 ELF64 и корректные границы таблиц/сегментов. Entry point должен лежать в отображённом user executable сегменте.

## Диагностика

- `RIP=0` в kernel mode обычно указывает на испорченный return frame или invalid saved context.
- `CR2` с user access bit указывает на user page fault; `error_code` bit 4 обозначает instruction fetch.
- Для exec сравнивайте ELF `readelf -l` диапазоны с mapped entrypoint и текущим CR3.
- Не добавляйте `printf` в частые syscall/IPC loops: сериализованный вывод способен менять планирование и скрывать исходную гонку.
